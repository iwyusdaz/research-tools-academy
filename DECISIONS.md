# Decisions

Design and build decisions, with alternatives and rationale. (The resume-specific scope decision is D1.)

| # | Decision | Alternatives considered | Rationale | Evidence / consequences |
|---|---|---|---|---|
| D1 | **No macOS GUI automation for Zotero screenshots.** All lessons written from the official Zotero documentation, each step verified for a stated version (Zotero 10.0.6, verified 2026-10-25), with schematic SVG diagrams labeled "Illustration, not an actual screenshot" and numbered callouts (number + outline, never color alone). **No fake screenshots.** | Install Zotero via Homebrew and drive the macOS GUI with screencapture; embed real screenshots from the web; skip figures entirely | GUI automation was out of scope and brittle across OS versions; web-scraped screenshots raise licensing and trust issues; skipping figures hurts comprehension. Schematics are version-stable, fully accessible, and honest about being illustrations | Schematic generator committed (`docs/assets/figures/generate-schematics.mjs`); version stamp on every lesson; maintenance plan makes re-verification cheap. A future build can add real annotated screenshots against the same shot structure |
| D2 | The dataset includes 17 **feature requests** (entry_type=feature), but they are **excluded from the knowledge-gap analysis** (n=128 used) | Exclude features from the dataset entirely; or include them in the fix-route analysis | Feature requests are real signal for a (fictional) product team but not education work; including them would inflate the "product" share and muddy the "is it training?" finding | Documented in the analysis method; 145 rows remain in the CSV for transparency |
| D3 | Troubleshooting tool covers the **top 5 issue themes** chosen on frequency *and* whether guided diagnosis helps (C1 ×2, C2, C2/C3, C5) — not strictly the 5 largest categories | Strictly top-5 categories (would include PDF-reader and mobile categories) | C6 (PDF reader) and C7 (mobile) problems are mostly genuine bugs where a guided flow adds little; C1 is split into its two distinct failure modes (no button / save fails) because the data shows they have different causes and fixes | `flows.json` maps each flow to CSV rows and official KB pages in the analysis §2.4 |
| D4 | **11 lessons** (4 getting started / 4 writing / 3 power user) instead of the plan's 10–12 with 3–4 power user lessons; "find and merge duplicates" folded into the organization lesson as a step | 12 lessons with a standalone duplicates lesson | The milestone contract (every lesson moves a milestone) cut a standalone duplicates lesson — duplicates emerge naturally after saving ~10 items, which is exactly when lesson 4 runs | `analysis/activation-milestones.md` lesson map |
| D5 | Power-user lessons map to **extended milestones E1–E2** (annotation workflow, team collaboration) instead of being cut for moving no core milestone | Cut the power user path to sync only | The support data shows 25% of questions in C5+C6 — real adoption pain beyond week 1; the milestone model distinguishes *time-to-value* (M1–M5) from *retention* (E1–E2) explicitly | Milestones doc distinguishes core vs. extended |
| D6 | Job aids exist as **standalone HTML + PDF** (not Jekyll pages) with their own disclaimer | Make them regular Jekyll pages and "print to PDF" at will | They must survive printing/sharing outside the site context (orientation handouts); a fixed, committed, single-page PDF is a stable artifact | `docs/job-aids/*.html`, `*.pdf`; print CSS tested via Chrome headless |
| D7 | Simulated-learner pipeline uses **3 model slots (A personas, B+C independent item review)** with agreement reporting | Single model for everything; or no judge phase | The shared evaluation standard requires ≥2 models and "a model never judges its own output"; the judge phase turns raw persona answers into actionable item analysis | `evaluation/run-simulations.mjs`; `.env.example` exactly per portfolio spec |
| D8 | `_config.yml` inside `docs/` (not repo root) | Root config with `source: docs` | GitHub Pages with a `/docs` source reads the config from `docs/` — a sibling repo hit this; root-level config was silently ignored | Verified in this repo's Pages build |
| D9 | Just the Docs pinned to **v0.12.0** | `main` branch of the theme; unpinned | Reproducible builds; v0.12.0 verified as the latest stable release on 2026-10-25 | `docs/_config.yml` |
| D10 | Lessons link "If it didn't work" to **flow anchors** (`troubleshoot/index.html#flow-<id>`) rather than deep links into individual steps | Deep-link each fix step | The tool's state is client-side; anchor-per-flow is robust while keeping one hop from symptom to flow | Flows carry stable `id`s in `flows.json` |
| D11 | Agent-review revision round (2026-10-26): **milestone definitions published in the metrics plan page** (summary table) with the GitHub link kept for full definitions; **badge wording "supports milestone Mx (setup)"** for setup lessons via a `milestone_kind` front-matter field rather than a new badge token | Separate milestones page; badge text "prepares M1"; leave badge as "moves" | One authoritative on-site location (the metrics plan already anchors time-to-value) beats a near-duplicate page; the label line carries the nuance without complicating the badge | Finding 7 and 12 of `evaluation/agent-review.md`; triage log in CHANGELOG 1.0.1 |
| D12 | **Deferred:** flow 3's macOS fix step bundles four sub-steps (reinstall, templates, permission grant, version check) — the simulated dashboard recommends giving the permission grant its own screen | Rebuild flow 3's macOS step into two screens now | Content-density improvement, not an error; the bundled step matches the official page's order and the keyboard tests pass. Deferred to the next content pass | Agent review §2.3; finding recorded in CHANGELOG 1.0.1 |
